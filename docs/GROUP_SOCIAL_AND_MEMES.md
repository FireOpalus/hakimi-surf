# 0.7.0：群聊防抖、看图与本地表情包

这次升级沿用现有 FastAPI、认证后的 OneBot 消息、SQLite 账本及物理隔离 Session。`google-genai>=3.2.0,<4` 不变：前置检查继续调用 `v1beta` 的 `gemini-decision-1`，生成继续调用 GA `v1` 的 `gemini-4-hydrogen` Interactions，并设置 `store=False`。没有新增模型、Node.js 构建流程或外部 CDN。

## 修改模块

| 模块 | 行为 |
| --- | --- |
| `group_pipeline.py`、`store.py`、`service.py` | 明确 `@他人` 的消息在模型调用前忽略；持久化同群防抖批次和短期相邻上下文，合并为一次处理 |
| `media.py`、`service.py` | 当前批次与紧邻三条群消息中提取至多两张图片，下载、缩图、标注发送者，再单独安全筛查 |
| `persona.py`、`reply_style.py`、`gemini.py` | 仅重写 PUBLIC 人设；静态前缀加入本地表情协议，公开回复限制为短句且去除波浪号 |
| `memes.py`、`meme_admin.py`、`admin_page.html`、`adapters.py` | 后台上传／预览／删除白名单表情，解析模型末尾标签，先发文字再以 base64 发本地图片 |

`requirements.txt` 与项目依赖已有 Pillow，本次直接复用；原有 `ffmpeg`、yt-dlp 与原片下载权限不受此升级改变。

## 群聊入口与防抖

Layer 0 只读取协议中真实的顶层 `at` 消息段。消息 `@` 了其他成员或外部 Bot，但没有 `@` 本 Bot，且直接文本没有「吉米奈」「哈基米」「大小姐」等唤醒词时，立即忽略，不下载图片、不预留模型费用、不调用 Decisions。转发内的文字、伪造昵称和文本角色标签不能充当协议身份；视频链接或引用也不会绕过这条抢话过滤。

通过原有群白名单、Bot／小黑屋过滤和互动策略后，同群消息进入 SQLite 防抖队列：

```dotenv
HAKIMI_GROUP_DEBOUNCE_SECONDS=1.8
HAKIMI_GROUP_DEBOUNCE_MAX_SECONDS=3.5
```

每次新消息重置 1.8 秒等待，但从首条消息算起最多等待 3.5 秒；达到批次容量限制会提前收束。一个批次只做一次对话生成、写入一条回复出箱任务。批次保留每位发言者的真实来源，不把混合消息拼成管理指令，也不把整个批次的违规判定归罪到最后一位发言者。群之间、群与私聊之间不合并；斜杠命令保持独立。原有去重、预算、处理期限和发送确认规则继续生效。

在 `at_only` 模式，首条 `@Bot` 开启窗口后，同群未再次 `@` 的补充句可以加入尚未到期的批次；没有已有触发批次时，普通消息仍不启动模型。每条原始消息保留独立身份，并在模型调用、出箱投递前再次核对全部参与者的准入，任何成员被屏蔽都会取消该批待发回复。重置群 Session 会同时取消已经排队但尚未处理的旧群消息，正在处理的任务由现有 epoch 校验拦截。

这两个参数在启动时读取，修改 `.env` 后需重启后端；设两者为 `0` 可恢复立即处理。这里的窗口独立于发送端原有自然延迟，也不改变 `/admin` 的 Session 压缩阈值。

`at_only` 群里没有唤醒 Bot 的普通图片消息可以进入短期相邻上下文，本身不触发模型；随后获准的提问才使用它。陌生群、黑名单、明确说给别人的消息不进入这个上下文。查询只看同群触发批次之前紧邻的三条消息，不查询 Owner 私聊。短期记录加密保存，最多保留五分钟、每群三十条及全局一千条；清空群 Session 同时清理相关短期记录。

## 看图与安全降级

每轮合计最多读取两张图片，优先本批次，再取紧邻三条群消息中的图片，重复 URL 去重。模型输入同时标注图片编号、发送者及「本批消息／紧邻群消息」来源；无法确认转发原作者时明确标注，不猜测归属。

图片只从受限 QQ HTTPS CDN 下载，校验 DNS 和实际连接地址，禁止内网地址及重定向，不携带账号 Cookie。每张下载总超时五秒；默认 `HAKIMI_IMAGE_MAX_BYTES=4194304`，即 4 MiB，代码硬上限为 5 MiB。继续遵守像素数上限，解码后去除元数据，等比缩至长边不超过 768px，以 JPEG、quality=80 提供给模型。GIF 仅读取第一帧，不传动画。

群消息先经过文字 Decisions 判断；确定继续处理后才下载相邻图片，再把图片作为独立来源送入 Decisions，通过后才进入 Interactions。相邻图片被拒绝不会给当前提问者记违规。加载失败对应 `[图片加载失败]` 占位，其余文字流程可以继续；系统提示要求不能猜图或把截图里的经历认成自己发生过的事。实际模型请求仍使用原有 Token 预留、结算和熔断账本。

## PUBLIC 人设与静态前缀

共享 `SYSTEM_INSTRUCTION` 和 Owner 私聊的 `OWNER_PERSONA_PROMPT` 保留原文，仅改写 `PUBLIC_PERSONA_PROMPT`：公开场景平视群友，Owner 也是熟人损友，不叫主人、不表忠心或讨好；社交回复限制为一到两句、三十字以内，去除波浪号。Owner 私聊仍使用原有专属风格，未套用公开短句裁剪或表情发送协议。

系统指令按「共享 SYSTEM → 身份差异段 → PUBLIC 本地表情规则与标签白名单 → 其他静态业务约束」构建。表情列表只在启动及管理员增删时更新缓存；时间、当前用户、会话记录、图片与当前消息留在动态输入末尾，避免把每条消息的变化写到静态前缀。前缀稳定有利于缓存复用，实际缓存量仍以账本记录为准。

表情协议仅进入 PUBLIC 社交生成，不进入日记、选片 JSON、压缩等后台任务。身份权限没有改变：只有真实 OneBot `OWNER_QQ_ID` 的私聊可读取已启用的 Owner 快照，普通好友使用 PUBLIC 和自己的独立 Session；本功能不会开启小本本。

## `/admin` 本地表情管理

通过已有 SSH 隧道打开 `http://127.0.0.1:12141/admin` 并登录，在「表情包管理」上传 `jpg/jpeg/png/gif/webp`。例如 `无语盯.jpg` 的标签为 `无语盯`；标签只接受一到二十四个汉字、字母、数字、下划线或连字符，重名需要先删除旧条目。

上传上限为 5 MiB、解码上限一千六百万像素，库最多一百张、合计 50 MiB。文件会去除元数据、缩至不超过 1024px 并转换为 JPEG；透明部分以白底合成，GIF／其他动画只保留第一帧。库位于 `HAKIMI_DATA_DIR/memes/`，容器默认 `/app/data/memes/`，与现有数据卷一起持久化。实际文件名由服务器生成，不使用模型文本或上传路径寻找文件。

后台以同源认证请求上传、预览和删除；所有 `/admin/api/memes` 接口继续受 `ADMIN_TOKEN` 及原有同源检查保护，不提供未认证的公开图片目录。未设置口令时管理接口仍返回 403。新增端点为：

| 方法与路径 | 用途 |
| --- | --- |
| `GET /admin/api/memes` | 标签、图片元数据及上传上限 |
| `POST /admin/api/memes/upload/{filename}` | 有上限的原始图片请求体上传，无需 multipart 依赖 |
| `GET /admin/api/memes/{id}/image` | 认证预览本地已注册 JPEG |
| `DELETE /admin/api/memes/{id}` | 立即撤销白名单并删除文件 |

模型只能在末尾选择一个 `[MEME:标签名]`；后端移除协议标签并检查本地白名单。已确认的纯文本先发送，等待 0.6 秒后再核对表情仍存在、Session／群准入仍有效，才读取本地 JPEG，以 OneBot `base64://…` 图片段发送。FastAPI 和 NapCat 各自在独立容器运行，无需共享本地图片路径，不发送 `file://` 或模型提供的外部图片 URL。未知、重复、格式错误的标签会被丢弃。

代码同时按会话限制为每四条公开回复最多尝试一张表情，计数及回复去重持久化；模型建议不能突破频控。管理员在文字发出后的间隔内删图，会阻止随后图片发送。图片失败只记脱敏事件，不重发已送达文字，不影响服务继续处理。

若模型只选了表情而没有文字，必须收到合法 OneBot `message_id` 确认后才写入对应会话记忆；被频控、删除或发送失败的纯表情不会伪装成已送达。沙盒只预览清理后的文字和候选标签，不发送图片、不修改实际频控。

## B 站 `buvid4` 按需补齐

`BILI_BUVID4` 和后台对应输入均可留空。已配置 `SESSDATA` 与 `bili_jct` 而缺少 `buvid4` 时，在首次获准的账号请求或原片凭证准备前，使用同一固定 User-Agent 请求：

```text
GET https://api.bilibili.com/x/frontend/finger/spi
读取 code=0 时的 data.b_4
```

请求沿用账号的代理、串行网络锁和 2～6 秒间隔，超时五秒，不跟随重定向；账号请求和 yt-dlp 使用同一固定 UA。成功值写回现有加密凭证记录，并加入之后的 Cookie。不会在服务启动时自动访问 B 站，也不会在无账号凭证时尝试补齐。

同一凭证版本最多自动尝试一次，尝试状态持久化，重启不会因失败无限请求。普通超时／坏响应允许缺少可选 `buvid4` 继续现有流程；在后台重新保存凭证会开启新一次补齐机会。热更新与请求串行，旧结果不会覆盖新凭证；后台只返回是否配置及固定状态，不回显完整 Cookie。

如果 SPI 或后续请求返回 `-101`、`-352`、`-412`、`v_voucher`，或 HTTP 401／403／412／429，仍立即停止当前轮次、进入原有十二小时冷却并走 Owner 模板告警。缺少 `buvid4` 的补齐不是验证码绕过，也不清除现有风控冷却；所有主聊天功能仍独立运行。

## SQLite 兼容迁移

启动采用 `CREATE TABLE IF NOT EXISTS` 增量创建以下表，不删除或重建既有 Session、账本、准入配置、巡逻日记或凭证表：

| 新表 | 关键字段及作用 |
| --- | --- |
| `group_debounce_batches` | `id, scope, first_at, ready_at, closed, count, chars`：同群批次、最晚到期和容量 |
| `group_debounce_items` | `job_id, batch_id`：既有任务与批次对应关系 |
| `group_recent_messages` | `event, scope, at, event_at, payload`：去重、群隔离、时序和加密短期消息 |
| `meme_library` | `id, label, filename, mime_type, digest, byte_size, width, height, created`：唯一标签、受控文件及完整性校验 |
| `meme_reply_frequency` | `scope, replies, last_meme_reply`：会话级每四次回复频控 |
| `meme_reply_reservations` | `reply_id, created`：同一回复不能重复消耗或发送表情 |
| `bili_device_state` | `id, fingerprint, attempted_at, status`：单一账号的凭证版本摘要与 SPI 尝试状态 |

既有 `outbox.payload` 继续加密，公开回复按需追加 `meme_tag`／`meme_eligible` 及批次原始 `participants` 字段；旧任务缺少这些字段仍可正常处理。`bili_credentials.payload` 在旧三项凭证基础上补缺省 `buvid4=""`，成功补齐后整体重新加密写入。会话的滚动摘要与热窗口表无需改结构。

升级前保留现有数据卷、加密密钥并按原运维方式备份 SQLite。不要删除数据库、重新初始化 `.env` 或执行 `docker compose down -v`。本说明描述代码和验收方法，不表示服务器已经完成升级。

## 验收方式

1. 在白名单群中只 `@` 其他成员，确认没有回复和新增模型费用；直接叫「大小姐」或 `@Bot` 时仍按群策略处理。
2. 在防抖窗口内连续发两条消息，确认一条简短文字回复；分别在不同群或私聊发送，确认上下文不混合。
3. 先发截图，再 `@Bot` 提问，确认能够说明图意及来源；用无效图片测试失败占位，不应编造图意。Owner 私聊内容不应出现在群回复中。
4. 在后台上传 `无语盯.jpg`，确认认证预览和删除可用。表情是否发送取决于语境、模型选择与频控，不要求每条消息发图；有表情时应先文字、后图片。
5. 保持 B 站写操作关闭，在后台保存小号凭证并点击已有 nav 测试；缺少 `buvid4` 时观察补齐状态。只在本地填写 Cookie，不贴入聊天；遇到冷却状态先人工处理登录或风控。

离线回归分别位于 `test_group_pipeline.py`、`test_media.py`、`test_memes.py`、`test_social_integration.py` 和 `test_bili_buvid4.py` 等测试文件；HTTP、Gemini 与 OneBot 外发使用模拟对象，不要求真实群聊、Cookie 或付费调用。
