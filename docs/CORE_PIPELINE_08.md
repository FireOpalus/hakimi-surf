# 0.8 核心管道、受控点名与记忆边界

本版在现有 FastAPI、SQLite、OneBot 和 Gemini 管道上增量升级。`google-genai>=3.2.0,<4`、Decisions `v1beta / gemini-decision-1`、Interactions `v1 / gemini-4-hydrogen` 保持不变；每次生成仍设置 `store=False`，本地全权管理历史，不使用 `previous_interaction_id`。

跨机部署见 [上海 NapCat／首尔主脑](CROSS_BORDER_DEPLOYMENT.md)。后端只监听宿主机回环 `12141`；公网新子域名 `qq.example.com` 只代理一条随机后缀 WS 路径，原主域名 DSH 站点保留。本文描述实现边界，不代表已完成两地真实账号联调。

## 收消息先落库，但未审核内容不进入热历史

接收顺序如下：

1. 适配器验证协议身份和事件，解析真实消息 ID、发送者昵称／ID、顶层 `at`、图片、引用和转发标识。
2. Layer 0 先检查是否明确 `@他人`：没有 `@Bot`、直接正文也没有唤醒词时静默忽略。群白名单、私聊名单、自回环、小黑屋和外部 Bot 权限仍先于付费 API；已知 Bot 默认连素材都不拉取。
3. 对获准处理的消息，以当前会话的接收锁串行执行 `SessionManager.receive()`。先把原始解析结果加密写入本会话 `received_messages`，再执行有上限的引用／转发 RPC，将展开结果更新到同一事件记录，随后加入持久化任务和防抖批次。不会等主脑生成完成才第一次写入。
4. `received_messages` 是不可信接收日志，初始状态为 `received`。它不直接用于主脑热历史，也不参与滚动摘要。每会话最多保留 200 条，最长 24 小时，并受配置的更短记忆 TTL 限制；关闭聊天记忆时仍保留这份有界接收日志用于引用回溯和处理去重。
5. 门卫通过且决定响应后，`admit_history()` 按事件去重，将本批获准原消息写入 `recent_messages`，并将接收日志标为 `screened`。拒绝或忽略的文本不会变成下一轮默认加载的热历史；若它后来被明确引用，仍作为本次不可信输入重新检查。

群聊热历史中的用户行标成 `[昵称(QQ:号码)]: 正文`，同时单独保存真实 `user_id`、`speaker`、`event_id`。昵称、转发昵称、正文里的 `[role=OWNER]` 都不能覆盖真实协议身份。

普通聊天生成结果通过现有输出审核后，先用 `reply()` 幂等写入本会话 assistant 历史，再加入 outbox，确保下一个串行批次能看见上一条生成结果。这条记录不代表 QQ 已确认送达：发送是否确认由 outbox 状态单独判断。纯表情回复必须收到有效 OneBot 回执才写入表情占位；主动 Owner 私信继续遵循发送确认后写入的既有规则。

## 统一防抖与会话串行

历史类名 `GroupPipeline` 保留兼容，但现已调度群聊、私聊和 `@Bot`：默认安静窗口 1.8 秒，新消息延后截止时间，距首条最多 3.5 秒。批次持久化于 `group_debounce_batches`／`group_debounce_items`，服务重启不会把同一组待处理消息拆成多次付费请求。

单批最多 8 条，同时限制转义后 UTF-8 大小为 `min(8000, max_context_bytes / 2)`；超出上限另起批次，不为拼批而截掉待审核原文。固定斜杠命令与获准外部 Bot 事件各自单独成批，仍经过防抖和同会话串行，以免拼接文本变成管理命令或混淆 Bot 消费次数。单条本身超过拼批大小上限时保留独立任务，不进入合并窗口。

`SessionScheduler.hold(session_scope)` 为每个真实会话维护引用计数的 `asyncio.Lock`：

- 接收锁保证本会话落库和引用展开顺序；对话锁覆盖读取历史、门卫、主脑以及回复写库。
- SQLite claim 同时避免两个消费者认领同会话在途任务；其他会话仍可独立推进。
- 主脑执行中到达的新触发消息继续先落库，进入待处理批次；锁释放后下一批重新读取最新 SQLite 热历史。忙碌期间可继续合并尚未认领的同会话批次，但不会突破批次数量和大小上限。
- `at_only` 群中未单独唤醒的后续短句，只能加入已有且尚在开放窗口内的真实唤醒批次；不会自行发起新的付费请求。明确 `@他人` 仍优先忽略。
- 混合群批次保留逐条真实身份；不会因其中出现 Owner 发言，就把普通成员内容变成 Owner 管理请求。

仍只支持一个 Uvicorn 进程、一个后端副本。Shanghai NapCat 是独立协议端，不是第二个读取同一 SQLite 的业务副本。

## 引用、转发与跨海取图

`MessageContextResolver` 在本会话接收日志中查 `reply.id`；没有本地记录时调用 `get_msg(message_id=...)`。远端响应必须匹配消息 ID、群／私聊类型以及真实群号或私聊目标。缺少足以证明同会话的字段、目标不匹配或 RPC 失败，统一降级为 `[引用消息暂不可读取]`，不搜索其他会话库。

最多回溯两条引用，展开文本保留原发送者，引用图随本轮输入携带。自己的已确认文本回执也缓存在原目标会话中，不另开“机器人自己的私聊库”。引用或转发中的 self ID 标成 `我自己(吉米奈喵)`；这帮助理解指代，不证明任意转发截图是真的，也不赋予权限。

`forward` 使用 `get_forward_msg(id=...)`。最多读取两个转发标识，每个保留前 20 个节点；文本总展开上限为 8000 字符，超限标注截断。内部节点保留昵称／ID，最多合入两张图。内层 `at`、斜杠命令和伪身份仅是数据，不能触发外层授权。RPC 有独立 8 秒超时；失败生成可见占位并写固定 WARNING 事件。

图片来源为当前批次、引用／转发图，以及紧邻的前三条本群消息；附近窗口最多回看五分钟。最终每轮最多两张，每张都标注发送者和来源。处理链路是：

1. 如消息段已声明 `file_size > 3,500,000` 字节，预先跳过，标记 `[大图略过]`。实际响应和解码字节数再次检查同一上限；配置更小上限时取更小值。
2. 优先通过已有 WS 调用 `get_image`，再尝试 `get_file`。只有实际 `base64` 字段才能解码为图像；服务全局 `Semaphore(1)` 串行这一取图阶段，每次 RPC 最多 10 秒。任何 `file://`、上海容器路径或裸本地路径都不会在首尔读取。
3. 没有 Base64 时，尝试已验证的 QQ CDN URL。下载客户端继续使用 `aiohttp`，保留连接时校验／固定公共 DNS 的现有 SSRF 防护；浏览器 UA、单次五秒超时、不跟随重定向、不发送 Cookie。
4. 兼容 TLS 只在这个 QQ 图片客户端内使用 `SECLEVEL=1` 与关闭证书验证；Gemini、B 站、Drive 的 TLS 设置不变。只有 `multimedia.nt.qq.com.cn` 和 `gchat.qpic.cn` 的 HTTPS 网络／超时、403 或 5xx 失败，才允许一次 HTTP 重试；拒绝来源、超限、重定向或无效响应体不触发降级。这个兼容兜底不提供可靠的源站身份／传输机密性，取得的图始终视为不可信素材。
5. Pillow 只取第一帧，校验像素数、处理方向、去除 EXIF 等元数据，等比缩放至最长边 768px，转 JPEG quality=80；失败使用 `[图片加载失败]`。服务日志只写阶段、异常类型和数值状态码，不写签名图片 URL 或原始字节。

私聊图随当前消息过门卫；群图在文本获准后进行独立 source 图文筛查，通过才交给主脑。附近成员图片导致的 source 拦截不会误记为当前发言者违规。任何下载失败都能退回文本，不会让群／私聊主服务崩溃。

## 仅公开群到 Owner 的单向背景

`public_interactions` 是主库中独立、加密的公开互动索引，记录的来源仅为**已确认文字发送成功**的 Bot 群聊回复，不遍历私聊数据库。

一条记录包含群名（缺失时用群号标识）、当批最多八位发言者的昵称／ID和每人最多 240 字的摘录、Bot 最多 400 字回复，以及时间。索引保留 12 小时、总量最多 500 条。它是可核对的截短对话，不会额外调用模型来编造“总结”。

只有真实 OneBot Owner 私聊请求能读取最近 12 小时内最新 15 条获准记录，作为 `[近期群聊巡逻记忆（只读背景）]` 加在动态输入中；还会受整体上下文字节上限裁剪。读取时重新校验来源群当前准入／关闭策略和发送者权限。普通好友、群聊和官方 QQ OpenID 都不能读取这块内容。

没有 `OWNER → PUBLIC` 反向路径。群聊始终只开本群会话库；Owner 快照仍有独立默认关闭开关，不因公开记忆桥启用。清空某群会话同时清除该群公开互动索引；清空 Owner 私聊不会删除独立的公开群索引，所以后续 Owner 请求仍可读取未过期、未撤销的公开背景。

## 受控点名与表情联合发送

所有固定输出规则、身份锚点和当前表情白名单在系统指令静态部分；本轮 `allowed_at_qqs`、聊天记录、图片、巡逻背景在动态输入中。模型只能建议标签，不能自行扩大可点名范围。

普通目标只来自当前模型上下文中真实出现的同群成员；Owner 也必须出现在本群窗口，不能仅因全局 Owner 配置就任意点名。永久去掉 self、`all`、`0`、小黑屋成员，默认去掉已知外部 Bot。默认一条回复最多一个不同目标，解析器绝对上限两个。

外部 Bot 的唯一例外须由真实 Owner 发起，顶层真实 `@` 仅指向一个目标，且明确说要互动。建议同时 `@Bot` 自身，以免命中“对别人说话”的 Layer 0。自然语言请求须为单条 Owner 原消息、通过安全门卫后才授权；否定、引述、假设、疑问等模糊表达保守拒绝。固定 `/bot-interact <话题>` 是另外的代码命令入口，也必须满足同一身份、真实点名和群策略校验。

许可保存在 `bot_dialogue_windows`：一次邀请的接话期限最多 120 秒，整群共享 10 分钟窗口最多两轮。再次邀请或改邀另一 Bot 不会重置已经使用的次数。每个获准 Bot 入站事件在 SQLite 事务中原子消费额度，写入 `bot_authorized_events`；服务内仅缓存这个真实事件的精确授权，绝不临时从全局黑名单移除目标。消费以接纳事件为准，即使后来门卫拒绝，也不会退回额度制造反复尝试。第三条事件在付费 API 前丢弃，私聊没有此例外。旧版本 `bot_interactions`／`bot_turns` 表可保留，但不会继续授予权限。

发送顺序固定：

1. 从结尾剥离唯一 `[MEME:标签]`，再解析 `[AT:纯数字ID]`，不把标签字符计入正文限长。
2. 合法目标生成 OneBot 数组 `at` 段，后接一个空格和正文。未知／超额／重复／私聊目标直接剥除标签，普通正文保留。
3. 发送前重新读取当前小黑屋和 Bot 许可，后台刚撤销的目标不再发 `at`。正文仍可发送，但对本条消息本身的准入被撤销时整条取消。
4. 有效本地表情按既有频率预算控制；正文发送后间隔 0.6 秒，重新校验再发 `base64://` 图片。不透传任意图片 URL，未知表情标签静默丢弃。

中文语境中的半角逗号转为全角；英文逗号、数字千位分隔、代码和 URL 不应被这项标点转换破坏。公开短单句不超过 35 字时去掉末尾句号，公开日常回复另受现有两句／30 字控制。`/admin` 展示已加载到 Prompt 的有效表情数和新 Bot 窗口用量，上传／删除后立即更新白名单。

## Prompt 顺序与双形态

普通聊天系统指令依次为共享 `SYSTEM_INSTRUCTION`、身份差异段、配置 self QQ 的固定身份锚点及安全规则；公开快聊再追加 AT 协议和表情白名单。时间、当前成员、滚动历史、图片及群巡逻背景不插入静态开头。Owner 私聊及日记／压缩等后台生成不注入公开聊天的表情协议。

- PUBLIC：把 Owner 当平视熟人损友，不喊主人、不献媚护主；听得懂网络梗并自然接话，不写冷漠杠精。不懂图片或未知细节时坦率承认，不复读装懂。0.8.0 群快聊使用 `low`；0.8.1 按后续要求将九场景默认统一为 `medium`，可在后台单独调回 `low` 或升至 `xhigh`，见 [模型策略](MODEL_POLICY.md)。
- OWNER：保留哈基米／小小姐／大小姐的亲近口吻，按话题自然 1～3 句，不机械分“感叹＋解释＋撒娇”三段。日常不背诵消息段、后端标签等实现说明；Owner 明确问技术时仍可如实回答。只有真实 Owner 私聊选择这套人设，默认 `medium`。

模型输出的人设表现不是身份认证机制；真实权限仍由协议身份和代码控制。

## 清空、修改与 epoch

每个物理会话库的 `rolling_state` 维护 `epoch` 和 `version`。后台重置、`/new-session` 或记忆关闭会删除热消息、摘要、接收日志并递增 epoch；还取消该会话尚未处理的入站任务、关闭防抖批次、清除邻近群上下文及该群的公开互动索引。

在途处理保留启动时 epoch，在付费调用前、用户历史／assistant 写库前、outbox 入队及最终发送前都检查。清空过程中返回的旧 LLM 结果不能重新写回或发出；异步压缩还对照 epoch／version，不能覆盖新手工摘要。后台编辑摘要也会递增 epoch，使旧生成结果失效。思考档位属于生成策略配置，不修改会话内容或 epoch。

已经提交给 OneBot 的网络请求无法撤回，已在 QQ 发出的内容、供应商记录及外部备份也不随本地清空删除。`sending` 状态崩溃或回执不确定时维持原来的 uncertain 语义，不自动重发。

## 预算时区与旧账本迁移

0.8 不仅设置容器 `TZ`，还实际让账本 `day()`、自然月、主动计划、免打扰和新审计计数按 `BOT_TIMEZONE` 计算。默认 `Asia/Shanghai` 的日界为北京时间 00:00，月界为本地每月 1 日，不取首尔宿主机 KST 或 UTC 日期。

`Store.open()` 首次在事务中运行 `initialize_calendar()`：

- 将旧聚合加密保存到 `usage_calendar_legacy`；按 `ledger_times.created` 的真实时间戳重新归入本地日／月。输入、输出、缓存、思考 Token 和可追溯费用一起重建。
- 保持 lifetime 聚合及累计总花销不变。没有真实时间戳的旧行不会伪造时间；已被裁剪的旧明细不能恢复成精确本地统计。后台 API 的 `usage.history.calendar` 明确标记历史覆盖不足。
- 对迁移当前日／月可能漏计的旧金额建立 `budget_calendar_carry` 保守占用，继续参与熔断，避免升级意外释放额度。后台单独显示“历史时区迁移保守占用（日／月）”，它不是新发生的真实消费，不重复增加 lifetime。
- 保守占用仅对应迁移当天／当月，越过相应本地边界自然不再计入；旧历史仍在归档表中。只有旧按日聚合、没有逐次时间的审计计数无法精确重分桶，新计数从升级后使用本地日界。
- 迁移幂等，记录已采用的时区；以后用不同 `BOT_TIMEZONE` 打开同库会拒绝启动，而不是悄悄再次改日界。不要通过改时区绕开预算。

管理 API 增加 `day_local`、`month_local`、`timezone`。旧 `day_utc`／`month_utc` 字段仅作兼容别名，其值已跟随本地预算周期，不应用来推断 UTC 日期。实际估算费用与保守扣账仍分别展示，缓存命中率和缓存／思考 Token 的既有统计规则保持。
