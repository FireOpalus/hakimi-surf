# v1.1.7：外部 Bot 阈值与冷历史合批提炼

[架构图](../architecture.html) 新增 [Bot 三路分流](../architecture.html#bot-routing) 和 [冷历史合批](../architecture.html#memory-batching)。群／私聊隔离、ADMIN_TOKEN、Fernet、SSRF 防护、事务预算、ACK 入史及现有部署拓扑继续沿用。

## Bot 接话规则

`BOT_QQ_IDS` 现在是已知外部 Bot 列表，接话门槛由 `BOT_REPLY_THRESHOLD`（默认 `0.85`）和 `HAKIMI_BOT_REPLY_THRESHOLDS` 的逐账号覆盖决定，均可在后台热调并加密持久化。

- 非邀请的有效阈值为 `1.00`：入站前静默丢弃，不调用模型。已知 Bot 私聊同样不进入互动通道。
- 阈值 `0.01–0.99`：仅在群准入和群策略允许时进入 Decisions；安全检查通过且 `should_reply` 达标才接话，真实 @ 也不能绕过这项门槛。该路径消耗正常 API 额度，仍受全局限流与预算约束。
- 真实 Owner 显式邀请：继续使用独立的单群两轮／10 分钟窗口及持久化事件授权，保留授权内的受控 @／引用。该轮数限制不应用于普通阈值路径。

阈值路径不添加旁听邻近上下文，出站清除自动 @／引用锚点；所有已知 Bot（含受邀 Bot）均不自动联网或解析 B 站视频。删除 Bot 同时删除其覆盖值；Owner／本机 ID 仍不可加入该列表。旧 admission 行合并新增环境默认字段加载，既有名单和私聊模式不改写；如果要保留旧版完全屏蔽行为，应将默认或指定 Bot 阈值设置为 `1.00`。

## 冷历史合批与费用检查

先检查全局预算和最小提炼费用，再通过 `peek()` 只读挑选同会话、同 epoch 的 pending 冷片，按创建顺序合并最多 64 片并检查字节预算。构造完整载荷后再次估算来源门卫、Flex 生成及输出门卫费用；不足则保留待办，不先消耗切片。

后台仅由 expiry 组成的小批次，在不足 24 条、不足 4096 字节且最早分片不足 30 分钟时暂缓；手动强制提炼不受该等待条件影响。真正领取时核对 `expected_ids`，记录 `batch_id` 和 `attempted_at`，各 API 仍独立事务预留。

生成前遇预算拒绝或供应商冷却，可恢复 pending。已尝试生成但结果不明的批次不自动重放；失败记录有限错误码，完成则统一标记 done。云端响应 schema 使用类型与枚举，本地逐条验证长度、范围、原话证据与归属，跳过单条无效事实，保留 epoch／版本／人工锁检查。

会话管理面板增加归档健康信息，包括状态计数、最早待办与最近尝试／成功／错误。沿用现有冷史及任务表，不重建账本、不改写不可变源片。`Store.can_reserve()` 是无扣款预检，与实际 `reserve()` 共用拒绝规则，不能替代正式预算预留。
